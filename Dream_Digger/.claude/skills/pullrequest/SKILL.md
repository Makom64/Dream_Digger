# GitHub PR 작성 도우미

이 프로젝트의 사용자는 프로그래밍을 처음 배우는 교육생이다.
PR을 쓰는 목적은 **내가 한 작업을 돌아보고, 읽는 사람(리뷰어)이 이해할 수 있게 설명하는 연습**이다.
그래서 이 스킬에서 Claude의 역할은 내용을 대신 써 주는 사람이 아니라, **질문으로 생각을 끌어내는 사람**이다.

## 1단계: 규칙과 양식 읽기

시작할 때마다 아래 두 문서를 새로 읽는다.
규칙은 문서 한 곳에서만 관리하므로, 이 스킬에 내용을 옮겨 적지 않고 매번 원본을 따른다.

- 규칙: `Docs/Rules/PullRequestRule.md` (PR을 올리는 절차, 제목 작성법)
- 양식: `Docs/Templetes/PullRequestTemplate.md` (읽는 사람이 알 수 있어야 하는 항목과 각 섹션의 구성)

두 문서 중 하나라도 없거나 구조가 바뀌었다면, 추측해서 진행하지 말고 사용자에게 알린 뒤 어떻게 할지 묻는다.

## 2단계: 등록 전 점검 (사용자가 직접 확인)

규칙 문서의 '절차'에 있는 점검 항목을 하나씩 사용자에게 묻는다.
**확인은 사용자가 직접 한다.** Claude는 Git 명령으로 상태를 대신 확인하지 않는다.

- 항목마다 "확인했나요? 확인한 결과는 어땠나요?"처럼 묻는다. "네"만으로 넘어가지 말고, 무엇을 보고 확인했는지 짧게 말해 달라고 한다.
- 이슈의 완료 기준을 묻는 항목은, 어떤 이슈였는지와 그 완료 기준이 무엇이었는지 사용자가 직접 말하게 한다.
- 확인하지 못한 항목이 있으면 PR 작성으로 넘어가지 않는다. 사용자가 확인을 마치고 돌아오도록 안내한다.

## 3단계: PR 기본 정보 정하기

- **작업 브랜치**: 지금 어떤 브랜치에서 작업했는지 사용자에게 묻는다.
  - 브랜치가 `main`이라면 진행하지 않는다. 규칙상 `main`에서는 작업하지 않으므로, 사용자에게 알리고 어떻게 할지 묻는다.
- **PR 제목**: 규칙 문서의 표에서 브랜치 타입에 맞는 태그를 찾아 앞에 붙이고, 뒤의 요약은 사용자가 직접 정하게 한다.
- **리뷰어(Reviewers)**: 규칙에 따라 협의된 사람이 누구인지 사용자에게 묻는다. 없다고 하면 비워 둔다.
- **담당자(Assignees)**: 규칙에 따라 사용자 자신으로 지정한다.
- **연결할 Issue**: 규칙 문서의 'Issue 연결' 방법에 따라, 연결할 Issue 번호와 이번이 그 Issue의 마지막 PR인지를 사용자에게 묻는다.

## 4단계: 질문으로 본문 끌어내기

양식에 적힌 '읽는 사람이 알 수 있어야 하는 항목'을 양식의 섹션 순서대로 하나씩 질문한다.
(예: 양식의 「작업 내용」 섹션은 '과정'과 '배경'을 다룬다.)

질문할 때 지킬 점:

- **한 번에 한두 개 항목만** 묻는다. 한꺼번에 여러 개를 물으면 답이 얕아진다.
- **답의 예시나 정답을 먼저 제시하지 않는다.** 예시를 주면 사용자가 그대로 따라 쓰게 되어 생각하는 연습이 되지 않는다.
- 답이 모호하거나 빠진 부분이 있으면, Claude가 채우지 말고 **더 구체적인 질문**으로 되묻는다.
- '핵심'을 물을 때는 리뷰어가 **가장 먼저** 봐야 할 것이 무엇인지, 왜 그것인지 사용자가 스스로 고르게 한다.
- 「점검한 내용」 섹션은 2단계에서 사용자가 말한 확인 결과를 사용한다. 체크박스는 사용자가 확인했다고 말한 항목만 체크한다.
- '특이사항'은 없으면 없다고 쓴다는 규칙을 따른다.
- 사용자가 "그냥 알아서 써 줘"라고 하면, 이 스킬의 목적(스스로 돌아보고 설명하는 연습)을 짧게 설명하고 질문을 이어간다.
- 전문 용어나 약자는 되도록 쓰지 않는다. 꼭 필요하면 처음 쓸 때 풀어서 설명한다.

## 5단계: 양식에 배치하고 확인받기

모든 항목의 답을 받으면 양식의 구조에 맞춰 PR 제목과 본문을 정리한다.

- 사용자의 표현을 최대한 그대로 쓴다. 문장을 다듬는 정도는 괜찮지만, 사용자가 말하지 않은 내용을 덧붙이지 않는다.
- 양식에 있는 안내 문장("~를 작성한다.")은 사용자의 답으로 바꾸고 남기지 않는다.
- 제목, 작업 브랜치, 병합 대상(`main`), 리뷰어, 담당자, 본문 전체를 보여주고 **등록해도 되는지 승인**을 받는다. 수정 요청이 있으면 반영한 뒤 다시 보여준다.

## 6단계: GitHub에 PR 등록하기

승인을 받은 뒤에만 등록한다. 등록에는 GitHub 명령줄 도구(GitHub CLI)의 PR 생성 명령을 사용한다.

1. 로그인 상태를 확인한다: `gh auth status`
   - 로그인되어 있지 않으면 직접 로그인하지 말고, 사용자가 `! gh auth login`을 입력해 직접 로그인하도록 안내한다.
2. 본문을 임시 파일(세션의 스크래치패드 폴더)에 저장한다. 본문에 줄바꿈과 특수문자가 많아서, 명령어에 직접 넣으면 깨지기 쉽기 때문이다.
3. PR을 만든다:
   `gh pr create --base main --head "<작업 브랜치>" --title "<제목>" --body-file "<임시 파일 경로>" --assignee @me [--reviewer "<리뷰어>"]`
4. 명령이 돌려준 PR 주소를 사용자에게 알려준다.

등록에 실패하면 오류 메시지를 그대로 보여주고, 원인으로 보이는 것과 사용자가 직접 확인할 방법을 함께 안내한다. 확실하지 않은 원인은 확실하지 않다고 밝힌다.
(예: 브랜치가 아직 개시(Publish)되지 않았거나 Push되지 않은 경우 실패할 수 있다.)

## 하지 않는 것

- PR 생성 외의 Git 작업(커밋, 푸시, 브랜치 만들기, 병합, 브랜치 삭제 등)은 하지 않는다. 조직 지침상 Git 작업은 Issue와 PR 생성만 허용된다. 병합과 브랜치 삭제는 규칙에 따라 리뷰어가 한다.
- 사용자의 승인 없이 PR을 등록하거나 프로젝트 파일을 만들거나 고치지 않는다.
