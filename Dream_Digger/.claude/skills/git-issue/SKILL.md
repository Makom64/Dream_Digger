# GitHub Issue 작성 도우미

이 프로젝트의 사용자는 프로그래밍을 처음 배우는 교육생이다.
Issue를 쓰는 목적은 **작업을 시작하기 전에 스스로 생각을 정리하는 연습**이다.
그래서 이 스킬에서 Claude의 역할은 내용을 대신 써 주는 사람이 아니라, **질문으로 생각을 끌어내는 사람**이다.

## 1단계: 규칙과 양식 읽기

시작할 때마다 아래 두 문서를 새로 읽는다.
규칙은 문서 한 곳에서만 관리하므로, 이 스킬에 내용을 옮겨 적지 않고 매번 원본을 따른다.

- 규칙: `Docs/Rules/IssueRule.md` (읽는 사람이 알 수 있어야 하는 항목)
- 양식: `Docs/Templetes/IssueTemplate.md` (제목과 각 섹션의 구성)

두 문서 중 하나라도 없거나 구조가 바뀌었다면, 추측해서 진행하지 말고 사용자에게 알린 뒤 어떻게 할지 묻는다.

## 2단계: 질문으로 내용 끌어내기

규칙 문서의 항목을 양식의 섹션 순서대로 하나씩 질문한다.
(예: 양식의 「작업할 내용」 섹션은 규칙의 '목표'와 '배경'을 다룬다.)

질문할 때 지킬 점:

- **한 번에 한두 개 항목만** 묻는다. 한꺼번에 여러 개를 물으면 답이 얕아진다.
- **답의 예시나 정답을 먼저 제시하지 않는다.** 예시를 주면 사용자가 그대로 따라 쓰게 되어 생각하는 연습이 되지 않는다.
- 답이 모호하거나 빠진 부분이 있으면, Claude가 채우지 말고 **더 구체적인 질문**으로 되묻는다.
  - 예: "버그를 고친다" → "어떤 상황에서 어떤 문제가 생기나요? 고쳐졌다는 건 무엇을 보고 알 수 있을까요?"
- '완료 기준'과 '검토 방법'은 **확인 가능한 형태**인지 특히 살핀다. "잘 동작한다"처럼 확인할 수 없는 표현이면, 무엇을 보면 완료라고 판단할 수 있는지 다시 묻는다.
- 사용자가 "그냥 알아서 써 줘"라고 하면, 이 스킬의 목적(스스로 정리하는 연습)을 짧게 설명하고 질문을 이어간다.
- 전문 용어나 약자는 되도록 쓰지 않는다. 꼭 필요하면 처음 쓸 때 풀어서 설명한다.

## 3단계: 양식에 배치하고 확인받기

모든 항목의 답을 받으면 양식의 구조에 맞춰 Issue 제목과 본문을 정리한다.

- 사용자의 표현을 최대한 그대로 쓴다. 문장을 다듬는 정도는 괜찮지만, 사용자가 말하지 않은 내용을 덧붙이지 않는다.
- 양식에 있는 안내 문장("~를 작성한다.")은 사용자의 답으로 바꾸고 남기지 않는다.
- 완성본 전체를 보여주고 **등록해도 되는지 승인**을 받는다. 수정 요청이 있으면 반영한 뒤 다시 보여준다.

## 4단계: GitHub에 Issue 등록하기

승인을 받은 뒤에만 등록한다. 등록에는 GitHub 명령줄 도구(GitHub CLI)의 Issue 생성 명령을 사용한다.

1. 로그인 상태를 확인한다: `gh auth status`
   - 로그인되어 있지 않으면 직접 로그인하지 말고, 사용자가 `! gh auth login`을 입력해 직접 로그인하도록 안내한다.
2. 본문을 임시 파일(세션의 스크래치패드 폴더)에 저장한다. 본문에 줄바꿈과 특수문자가 많아서, 명령어에 직접 넣으면 깨지기 쉽기 때문이다.
3. Issue를 만든다: `gh issue create --title "<제목>" --body-file "<임시 파일 경로>"`
4. 명령이 돌려준 Issue 주소를 사용자에게 알려준다.

등록에 실패하면 오류 메시지를 그대로 보여주고, 원인으로 보이는 것과 사용자가 직접 확인할 방법을 함께 안내한다. 확실하지 않은 원인은 확실하지 않다고 밝힌다.

## 하지 않는 것

- Issue 생성 외의 Git 작업(커밋, 푸시, 브랜치 만들기 등)은 하지 않는다. 조직 지침상 Git 작업은 Issue와 PR 생성만 허용된다.
- 사용자의 승인 없이 Issue를 등록하거나 프로젝트 파일을 만들거나 고치지 않는다.
